# ADR: 端口 + 适配器，契约自持

状态：已实施
范围：`src/domain`、`src/adapters`、`src/pipeline`、`src/app`

## 背景

重构前系统已经"模块化"，但边界仍然绑死在第一个实现上：

- `IVioBackend` 的 7 个方法里 5 个收发 `gtsam` 类型（`Pose3` / `NavState` /
  `ConstantBias` / `Values`），`common/` 还把 `gtsam` 链进了 `myslam_common`。
  因此"换掉 gtsam"在接口层就不成立——新实现必须先引入 gtsam 才能实现接口；
- `ProjectionModel` 的核心方法 `cal3()` 只能返回 `gtsam::Cal3_S2`，注释里
  "新增 MEI 实现、后端一行不改"实际不成立；相机数学散落在三处；
- `CameraFrame` 只有 `uv / uvNorm / isNew`，是"某个前端 + 某个投影模型"的形状：
  没有图像、没有协方差、没有原始像素、没有相机-IMU 时间偏移；
- 时间同步（零阶保持、断档、截断）手写在回放循环里，约 90 行交织着读图与日志，无法单测；
- 恢复策略焊在编排层：`KEYFRAME_FAILED → reset()`，后端无法表达"该局部恢复还是该重定位"；
- 后端注入只对第一次生效：`VioPipeline::reset()` 无条件 `make_unique<VioBackend>`，
  第一次重建就把注入的实现静默换掉了；
- 配置是一个约 40 字段的扁平结构，装配层逐字段手抄；没有"用哪个后端"这个概念。

## 决策

依赖方向改为 **domain ← 适配器 ← 编排**，契约类型由项目自己定义。

1. **`src/domain/` 自持契约**。位姿、偏置、状态、观测、关键帧、估计快照都是领域类型，
   只依赖 Eigen（作为数值标量扩展）与日志。任何第三方求解器或视觉库都不得出现在这里。
2. **端口以能力而非类型描述需求**。需要针孔标定的适配器查询
   `IPinholeCalibration` 能力对象，因此真实 MEI 模型配给只认针孔的优化器会在**装配期**
   被拒绝，而不是在运行期算出错误的雅可比。
3. **IMU 窗口随关键帧交付**。`addKeyframe(keyframe, imuSlice)` 把"自上个关键帧以来的
   IMU"作为数据交给估计器，估计器自行决定预积分/批量/其他。"必须逐样本流式喂入"
   不再是被强加的假设。
4. **恢复语义进契约**。`StepResult` 携带 `StepStatus` 与 `RecoveryAction`。视觉中断
   返回 `NONE`（重建坐标系毫无作用），惯性失稳返回 `RESET_PIPELINE`，估计器自带的
   重定位返回 `RELOCALIZE`。编排层只执行，不猜。
5. **工厂与注册表**。估计器按配置名从注册表创建；重建复用同一个工厂。未知名字明确
   失败并列出已注册项，没有静默回退——静默回退正是旧代码里那个 reset 缺陷的同类错误。
6. **时间同步独立成可单测组件**（`domain::TimeSynchronizer`）。
7. **配置分组成谁消费**：camera / imu / vision / initialization / estimator / health。
   换估计器只改 `estimator` 组与注册名，其余不变。

## 实施中的两个真实发现

契约收窄会暴露原本被"共享同一个具体实现"掩盖的错误，两处都在实施中复现并修复：

- **就地重建必须保留未消费的 IMU 区间**。`RESET_ESTIMATOR` 重建出的新估计器锚定在
  「上一个成功关键帧」初始化，而它还没消费那段 IMU。清空窗口会让下一个关键帧只拿到
  重建之后的尾段，预积分因子却声称覆盖「锚点 → 新关键帧」——积分时长与关键帧时间间隔
  错位。代价是窗口可能跨重建增长，因此连续就地重建设有上限（3 次），超过后退化为
  完整重置，把内存与算力封顶。
- **恢复后必须保留三角化基线**。`recoverSmoother()` 曾顺手清空 `previousObservations_`，
  而锚点关键帧仍在窗口里：恢复后的下一个关键帧因此无处可比，三角化被整体跳过一帧，
  与"恢复后基线更长、更容易重建路标"的意图正相反。现在保留锚点的观测。
- **首个关键帧的观测必须随先验一起传入**。把 `initialize` 的参数从"编号 + 状态"收窄
  时曾只传编号，估计器因此丢失第一帧观测作为三角化基线，RMSE 从 0.091 退化到 0.18。
  接口现在传整个 `Keyframe`。
- **跨帧几何量不能在不同参考系里比较**。曾把关键帧视差改成"两条 `normalized` 射线
  的夹角 × 焦距"，但两条射线分属两帧各自的相机系，夹角不是视差：20 px 的判据被压到
  6 px，关键帧节奏改变、RMSE 退化到 0.28。现在像素差是权威度量；观测由估计器声明的
  模型产生，因此配置里的像素阈值与观测像素同源。

## 收益（可验证）

- `myslam::pipeline` 只链接 `Eigen3::Eigen` 与日志。一个只链接该 target 的独立程序在
  干净工程里能编译链接，不引入 gtsam 或 OpenCV。
- 第二个后端 `imu_only` 与 gtsam 后端跑同一份流水线、同一份数据，仅配置名不同。
- `reset()` **不会**换回默认实现：它要么通过调用方提供的工厂重建，要么明确失败并把
  流水线标为无效。需要注意的边界是：重建产生的是**新实例**，不是原来的那个对象；
  契约保证的是"工厂被复用、观测模型不变"，而不是"同一个对象存活"。测试同时覆盖了
  `RESET_ESTIMATOR` 的可达路径。
- RMSE / 关键帧数与重构前逐位一致（0.0913 / 24），四个测试目标全部通过。

## 代价与不做的事

- **不做动态插件**：共享库加载带来 ABI、搜索路径与生命周期问题，当前规模收益为零。
  注册发生在编译期。
- **没有给每个小部件都造接口**：初始化器、外推器、关键帧决策器留在领域层作为具体类。
  它们不是要替换的技术点，抽象它们只会把流水线变成消息总线。
- **`common/` 里仍有数据型结构**（`dataset_config`、`ply_export`）：它们是非算法数据，
  不属于契约，也不需要被替换。
- **时间偏移是固定常数**，不做在线估计（`vio.timeOffsetSeconds`）。在线估计是一个
  独立的算法课题，不是这次架构调整的一部分。
