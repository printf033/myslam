# ADR 0002: 地图世代、位姿图与位置识别

状态：已实施（位置识别仅契约，参考实现明确缺席）
范围：`src/domain/types.hpp`、`src/domain/status.hpp`、`src/domain/pose_graph.hpp`、
`src/domain/place_recognition.hpp`、`src/adapters/gtsam/pose_graph.hpp`、
`src/pipeline/pipeline.hpp`、`src/common/config_summary.hpp`

## 背景

ADR 0001 把契约收回 `domain/`，解掉了「换后端要先引入后端」这个问题。但它
解决的是**同一条轨迹内**的可替换性。系统仍然有两个结构性缺口，README 的
「限制」章节自己写着：

- 无回环检测与全局重定位，误差随时间累积；
- 无地图持久化，路标随边缘化窗口回收。

这两个缺口有同一个根源：**坐标系只有「活着」与「没了」两种状态**。

1. `RecoveryAction::RELOCALIZE` 在 ADR 0001 里被写进契约，注释是「由估计器
   自行重定位（上层不得重建坐标系）」。但没有任何容器能装下「被重新定位到的
   那张地图」——`reset()` 一执行，历史就没了。这个枚举值是一个无法实现的承诺。
2. 固定滞后窗口之外，关键帧位姿不再被修正。窗口内的精度与窗口外的漂移是两件
   不同的事，靠调 `slidingWindowLag` 无法同时满足：拉长窗口解决漂移，代价是
   每帧求解规模与延迟一起增长。

对照 ORB-SLAM3 的做法（`Atlas` 多地图 + 三层优化 + 共视图/生成树/回环边），
可以确认这三件事是可分离的：地图身份（坐标系世代）、长期一致性（位姿图）、
外观检索（位置识别）。本 ADR 只做前两件，第三件只定契约。

## 决策

### 1. 地图身份进入领域类型

`MapId` 与 `KeyframeState`/`LandmarkEstimate` 的 `mapId` 字段进入
`domain/types.hpp`。`MapInfo{activeMap, revision, mapCount}` 描述当前世代。

关键语义改变：**`reset()` 不再丢弃历史，而是切换地图世代**。

```
RESET_PIPELINE  →  ++activeMap，旧地图的节点留在位姿图里
```

`RELOCALIZE` 因此第一次有了落点：它要回到的是某个具体的 `MapId`，而不是
一个已经不存在的东西。

### 2. 地图版本号 `revision` 单调递增

新增节点、新增边、估计器就地重建、完整重置、位姿图修正历史位姿——每一项都让
`revision` 前进。消费者（可视化、导出、UI）据此判断「手上这份快照是否过期」。

实施中发现的真实缺陷：第一版只在重建与优化时递增，于是**正常追踪期间新增的
关键帧不推进版本号**。消费者若按 `revision` 做增量刷新，会漏掉后续所有关键帧，
而这个问题不会让任何断言失败——它在测试里以「registering keyframes advances the
map revision」的形式暴露出来。版本号的语义必须是「地图内容」，不是「地图的
结构事件」。

### 3. 位姿图是独立端口，不是估计器的一部分

`IPoseGraph` 只存关键帧位姿与相对观测（共视边），不存路标。优化规模与路标数
无关，因此可以覆盖整段历史。参考实现 `adapters/gtsam/pose_graph.hpp` 用批量 LM。

为什么是批量 LM 而不是 iSAM2：位姿图的规模是「关键帧数」，秒级插入，几分钟的
序列也就几百个节点，批量 LM 是毫秒级。iSAM2 的增量结构（贝叶斯树维护、变量
重排序）在这个规模上纯属负债。翻转条件写进了代码注释：节点到万级，或需要每帧
优化的实时闭环。

为什么用 `shared_ptr` 而不是 `unique_ptr`：位姿图必须**跨流水线重建存活**。
丢失后重开地图时，新流水线要接着往同一张图里写；每段各建一张图会让「长期轨迹」
只剩最后一段，多地图退化成「多次互不相干的单地图运行」。所有权留在调用方
（`VioBenchmark` / `ReplayRunner`），流水线只借用。

边的协方差从**共视观测数**推出，而不是把两个绝对位姿的边际协方差相加：相邻
关键帧的漂移高度相关，相加会系统性高估相对误差，让位姿图几乎不修正任何东西。
按 `1/n` 收缩方差（标准差 `1/√n`），不用线性 `1/n`——后者会让共视 200 个点的边
获得比绝对位姿还小两个量级的方差，把整张图钉死在一条边上。

### 4. 视觉退化不得触发坐标系重建

这是 ADR 0001 里已经写进 `Degradation` 注释、但没有机制执行的一条：

> `VISUAL` 是外部观测退化（变暗、遮挡、无纹理），重建毫无作用——下一帧图像
> 依旧是黑的，重建只会让坐标系反复归零。

旧实现里估计器返回 `RESET_PIPELINE` 就直接执行。现在流水线在动作执行前过一道
门（`gateRecovery`）：

| 请求 | 条件 | 实际执行 |
| :--- | :--- | :--- |
| `RESET_ESTIMATOR` | — | 原样执行（保留坐标系） |
| `RESET_PIPELINE` + `Degradation::VISUAL` | — | `NONE`（重建不会让图像变好） |
| `RESET_PIPELINE` + 非视觉 | 连续失败 < `lostGraceSeconds` | `NONE`（保持坐标系继续尝试） |
| `RESET_PIPELINE` + 非视觉 | 连续失败 ≥ `lostGraceSeconds` | 原样执行 |
| `RELOCALIZE` | 无识别器 | `NONE` + 警告（不静默降级成重建） |
| `RELOCALIZE` | 有识别器 | 原样透传 |

宽限必须是**连续**计时：中间成功一帧就把 `lostSince_` 清零。否则长时间运行里
零星的单帧失败会累积到超时，在图像其实一直正常的情况下把坐标系切成两段。

### 5. 位置识别只定契约，参考实现明确缺席

`IPlaceRecognizer` 定义「索引 → 候选 → 调用方验证」这条链的分解方式，但不提供
参考实现。理由写进了头文件：可靠的跨地图检索需要**外观描述子**，而
`Observation` 当前只有像素、射线与编号；编号由前端跨帧维护，重建后必然重置，
不能当作跨会话的身份。

用一个「像素直方图相似度」凑一个能编译的参考实现是可以的，但它给出的候选没有
任何可验证的召回率——比缺席更危险，因为它会诱使上层把 `RELOCALIZE` 当成已可用。
缺席必须表现为**明确失败**（`gateRecovery` 返回 `NONE` 并告警），而不是一个安静
跑错的重定位。

### 6. 生效配置摘要是唯一实现

七个分组（相机/外参/IMU/视觉/前端/门控/初始化/估计器/健康/地图/运行时）由
`common/config_summary.hpp` 的 `summarizeConfig` 统一产出，`VioBenchmark` 与
`ReplayRunner` 都调用它。

两处各写一份的后果不是「多写几行」，而是两份会各自漏掉不同的字段，而**哪一个
漏了都没有任何机制能发现**——这正是摘要存在的理由。返回 `std::string` 而不是
直接打日志，是为了让测试能断言「每个分组都出现」。

## 收益（可验证）

- `myslam_pose_graph_test`：38 项。人工构造 25 cm 的 y 漂移，优化后压到 1 mm
  以内；锚点不被移动；两张地图互不污染；无修正时版本号不前进；累积航向误差同样
  被修正；非有限位姿被 `finitePose` 拒绝（含四元数分量）。
- `myslam_test`：478 项。新增覆盖：
  - 首帧登记为锚点（无协方差），第二条关键帧带协方差并入图；
  - 共视观测数是**测出来的**，不是默认值；
  - `reset()` 后 `activeMap` 前进、旧地图节点存活、新地图有自己的锚点；
  - `StubPoseGraph::optimizeCalls >= 1`——优化路径真的被调用；
  - 视觉退化在远超宽限的时刻仍不重建，但失败本身照常上报；
  - 宽限内不重建、超限才重建、中间成功一次会重置计时；
  - 无识别器时 `RELOCALIZE` 不被执行也不降级；有识别器时原样透传；
  - 无位姿图时世代计数仍然前进；
  - 空观测关键帧之后，共视边**不得**借用中断前的基线（共视数必须为 0）；
  - 位姿图宣称修正时，地图版本号在登记之外再前进一次。
- RMSE 与重构前一致（仿真 0.0575 m、24 个关键帧）：位姿图是旁路，不改变估计器
  的输出，这一点由精度门禁守住。

## 实施后再审查发现的缺陷

第一版实现通过全部测试后，逐行复查又找出四处真实缺陷。记录在此，因为它们都是
「测试绿了但它仍然错」的类型——这正是需要机制而不是断言的地方。

1. **共视数借用了错误的基线**。`registerPoseGraphEdge` 用
   `lastKeyframeObservations_` 算共视，而那份基线在「空观测关键帧」时被刻意保留为
   更早的一帧（关键帧决策器需要一条可比基线）。于是边的 `from` 端点是空帧、观测
   却来自更早的帧，共视数虚高——位姿图据此给一条「两帧之间毫无共同特征」的边分配
   了它不配有的信息量。修复：位姿图单独维护 `lastPoseGraphObservations_`，无条件
   跟随每一帧更新。反向验证：恢复旧代码后新测试立即失败。

2. **`mapCount` 依赖可选的旁路组件**。旧实现用
   `max(自身, poseGraph_->mapCount())` 兜底，未注入位姿图时两张地图跑完 `mapCount`
   仍是 1。修复：`mapCount = activeMap + 1`，与是否注入位姿图无关。「世代数」与
   「有节点的地图数」是两件事，位姿图重建后立刻结束会产生没有节点的世代。

3. **日志刷屏**。视觉退化与丢失宽限都是**持续**状态，逐帧告警会把同一条信息重复
   几十次，把真正的新事件挤出视野。修复：告警限流，状态变化时重新打开。

4. **失败与「没有漂移」在返回值上不可区分**。两者都返回 `false`，若前者也不打日志、
   不计数，位姿图持续失效时外部只能看到「每次都没有修正」，与正常工作完全一致。
   修复：优化失败计数并告警。
5. **写回缺少有限性校验（防御性加固）**。原实现一边算一边写回，一旦优化值里混进
   NaN 就会落到节点位姿里，`longTermTrajectory()` 随后把 NaN 交给调用方。实测中
   没有构造出这个输入（gtsam 4.3 在零协方差下既不抛异常也没把 NaN 写进结果，只在
   内部打印了诊断），因此这是按「不能让外部原因决定内部状态是否有效」做的加固，
   不是观测到的故障。修复：先整体校验再统一写回（`finitePose`），任一非有限即整批
   丢弃并计数；`finitePose` 本身单独可测，不依赖 gtsam 的退化行为。

## 代价与不做的事

- **位姿图在短序列上看不出收益**。5 秒仿真里估计器本身没有可见漂移，`optimize()`
  返回 `false`（无修正），日志里也确实不出现「修正了历史位姿」。这是正确行为，
  不是缺陷；它的价值要在分钟级、有回访的序列上才显现，而仓库里目前没有这样的
  数据源。
- **不做回环检测**。闭环要求外观检索、整图 Sim3 变换、地图合并，是一条长链。
  位姿图与地图身份是它的前置条件，先把前置条件做扎实。
- **不做地图持久化**。位姿图在内存里，进程结束即丢。持久化需要显式 schema 与
  版本号；ADR 0001 已经明确不走 `boost::serialization` 的整图黑盒。
- **`placeRecognitionCandidates` 目前没有消费者**。配置字段先留着，等实现到位；
  加它是因为宽限与候选数是同一个决策域（丢失后怎么办）的两个参数。
- **`IEstimator::setActiveMap` 是可选接口**。只支持单地图的后端可以忽略它，代价是
  快照里所有 `mapId` 都是 0，调用方必须自己用 `pipeline.mapInfo()` 补齐。没有把
  它设成 `= 0` 是为了不强迫纯 IMU 那类后端实现一个对它无意义的设置器。
